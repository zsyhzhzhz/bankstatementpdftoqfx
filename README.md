# 对账单 PDF 转 QFX

本地网页小工具：上传银行/信用卡对账单 PDF，自动提取交易记录，
核对/修正后一键生成可导入 Quicken 等财务软件的 `.qfx` 文件。

提供两种使用方式：

1. **`index.html`（单文件离线版，推荐日常使用）**：双击直接在浏览器打开，
   无需安装 Python/启动服务，PDF 解析、OCR 识别和 QFX 生成全部在浏览器
   本地完成，PDF 内容不会发往任何服务器。依赖同目录下的 `vendor/pdfjs/`
   （PDF.js 解析引擎）和 `vendor/tesseract/`（OCR 引擎，仅扫描件用得到），
   均已随项目一起提供，纯离线可用，**请勿单独移动/分发 `index.html`，
   需连同 `vendor/` 文件夹一起**。
2. **Flask 版（`app/` + `templates/` + `static/`）**：功能等价，用 Python
   实现，需要 `./run.sh` 启动本地服务后在浏览器访问，适合需要在 Python
   侧继续扩展解析规则的场景。

两个版本的解析/生成逻辑是分别用 JS 和 Python 实现的等价移植，核对流程
和使用步骤完全一致（见下文）。

## 设计思路

不同银行的对账单 PDF 版式千差万别，很难写出一套对所有银行都 100% 准确
的解析规则。因此本工具采用「自动提取 + 人工核对」的流程：

1. **自动提取**：用 `pdfplumber` 读取 PDF 中的表格，通过关键字（中英文皆支持，
   如“交易日期/摘要/借方/贷方/金额/余额”等）自动识别表头列，解析出交易记录
   和账户信息（账号、户名、开户行、币种、账单周期、期初/期末余额）。
   如果 PDF 没有规整的表格结构，会自动降级为按文本行的正则兜底解析。
   如果 PDF 完全没有文字层（扫描件/图片型 PDF），两个版本都会自动改用 OCR
   文字识别兜底（见下方「OCR 扫描件支持」）。
2. **人工核对**：解析结果会展示在网页的可编辑表格中，用户可以修改任何
   字段、增删行，纠正自动解析的错误（例如日期识别失败、金额正负搞反等）。
3. **生成 QFX**：核对无误后点击生成，后端按 OFX 1.02 SGML 规范拼出 `.qfx`
   文件供下载，支持储蓄卡/借记卡（`BANKACCTFROM`）和信用卡（`CCACCTFROM`）
   两种账户类型。

## 运行

### 方式一：单文件离线版（推荐）

直接双击 `index.html`（或拖进浏览器）打开即可使用。

> 如果你的浏览器出于安全策略限制了本地文件间的资源加载（表现为
> “PDF 引擎加载失败”），可以退而用一个最简单的本地静态服务器打开，
> 效果完全相同：
> ```bash
> cd "对账单PDF转QFX"
> python3 -m http.server 8899
> # 然后浏览器打开 http://127.0.0.1:8899/index.html
> ```

### 方式二：Flask 版

```bash
./run.sh
```

首次运行会自动创建虚拟环境并安装依赖，然后在
[http://127.0.0.1:8765](http://127.0.0.1:8765) 启动服务，浏览器打开即可使用。

也可以手动执行：

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m app.main
```

### OCR 扫描件支持

如果上传的 PDF 是扫描件/图片型 PDF（没有文字层，提取不到任何文字），
两个版本都会自动改用 OCR 文字识别来兜底解析，无需手动开启。OCR 引擎
用的都是 [tesseract.js](https://github.com/naptha/tesseract.js)（纯
JS + WASM，不依赖系统安装的 `tesseract`/Homebrew）：

- **`index.html`**：OCR 引擎（`tesseract.min.js`/`worker.min.js`/WASM
  核心/`eng.traineddata` 英文语言包，共约 16MB）已经打包在
  `vendor/tesseract/` 目录下，随项目一起分发即可离线使用，无需额外安装
  任何东西。遇到扫描件时会把 PDF 每页渲染到一个 `<canvas>` 上交给
  tesseract.js 识别，再按坐标重建表格，逻辑和 Flask 版是同一套移植。
  > 双击直接打开 `index.html` 时，部分浏览器出于安全策略会限制本地
  > 文件之间加载 OCR 的语言包/WASM 核心文件（和前面 PDF 引擎可能遇到
  > 的限制是同一类问题），如果 OCR 一直卡住或报错，同样可以改用本地
  > 静态服务器打开（见上方「方式一」的说明）。
- **Flask 版**：Python 侧通过 `app/ocr.py` 调用 PyMuPDF 把 PDF 每页
  渲染成图片，再用 Node.js 子进程调用 `app/ocr_node/recognize.js`
  （tesseract.js 的 Node 版）识别文字、按坐标重建表格。首次使用前需要
  额外装一次 Node 依赖：
  ```bash
  cd app/ocr_node
  npm install
  ```

> ⚠️ **OCR 识别可靠性明显低于文字层 PDF 解析**，尤其是扫描质量较差、
> 有倾斜/水印干扰的对账单：账号、银行名称、期初/期末余额这类"整份文件
> 只出现一两次"的关键信息通常能可靠识别，但逐条交易的具体日期/金额
> 出错率较高（常见错误：小数点识别丢失导致金额放大千倍、日期年份识别
> 错乱、行与行之间对不齐）。解析结果里会有明确的中文警告提示哪些字段
> 被清空待填、以及"逐条金额加总"与"对账单期初/期末余额算出的应有净
> 变动"是否对得上；**对不上时务必对照原始 PDF 图片逐条人工核对，不要
> 直接信任 OCR 给出的金额**。

## 使用步骤

1. 打开网页，选择对账单 PDF，点击「解析 PDF」。
2. 核对/修正「账户信息」（账号、账户类型、币种、账单周期、期初/期末余额等）。
3. 核对/修正「交易记录」表格：
   - 金额：**收入/存入为正数，支出/取出为负数**。
   - 可直接编辑单元格，也可以增删行。
   - 日期/金额不完整的行会自动标红提示。
4. 点击「生成并下载 QFX」，浏览器会下载生成的 `.qfx` 文件，导入到 Quicken
   等软件即可。

## 项目结构

```
index.html                单文件离线版：解析+生成逻辑都内联在一个 <script> 里
vendor/pdfjs/              PDF.js 引擎 + cmaps 字体映射表（index.html 依赖，需一起分发）
vendor/tesseract/          tesseract.js OCR 引擎 + 英文语言包（index.html 处理扫描件时依赖，需一起分发）

app/
  parser.py   PDF 解析：表格识别、账户信息提取、日期/金额归一化
  ocr.py      扫描件 PDF 的 OCR 兜底解析（渲染成图 + tesseract.js 识别 + 表格重建）
  ocr_node/   OCR 引擎用到的 Node.js 依赖（tesseract.js），需单独 `npm install`
  qfx.py      QFX（OFX SGML）文件生成
  main.py     Flask 路由：/api/parse、/api/generate
templates/index.html   Flask 版前端页面
static/app.js, style.css   Flask 版前端逻辑与样式
samples/make_sample_pdf.py  生成一份模拟对账单 PDF，用于自测（非真实银行格式）
```

## 已知局限 / 后续可优化方向

- 自动解析基于关键字启发式，遇到没见过的版式可能提取不全或列对应错误，
  这时请以网页上的可编辑表格手动修正为准。
- 账号/银行名称/账户类型（储蓄卡 vs 信用卡）等信息也是启发式猜测，务必
  在生成前核对「② 账户信息」区块。
- 如果你有具体银行的真实对账单样本，可以把它的表头关键字或版式特点
  告诉我，我可以在 `app/parser.py` 里针对性地补充解析规则，提升准确率。
- 目前 `FITID`（交易唯一标识）基于账号+日期+描述+金额哈希生成，重复导入
  同一批数据一般不会产生重复交易，但如果同一天有多笔完全相同的交易
  （日期、描述、金额都一样），仍建议导入后人工核对一下。
- `PDF/` 文件夹里的真实美国银行/信用社对账单（Chase、Bank of America、
  RBFCU）已经针对性适配并用对账单自身打印的合计数字核对过，`index.html`
  和 `app/parser.py` 两个版本的解析结果完全一致：
  - **Chase**（分节叙述式，单栏，"MM/DD" 无年份）：94 笔交易，存款
    $120,019.62、支出合计 -$106,050.32，与对账单一致。
  - **Bank of America**（分节叙述式，支票列表双栏并排）：203 笔交易，
    存款 $427,842.97、支出合计 -$395,926.39，期初/期末余额与对账单一致。
  - **RBFCU**（信用社，存款/支票列表左右双栏排版，需要按 PDF 原始文本流
    顺序而非视觉坐标解析）：25 笔交易，贷方合计 $47,866.50、借方合计
    -$1,486.06，与对账单"Total Credits/Total Debits"完全一致。
  - `2026.01-04 Bank stmt.pdf` 是扫描件（没有文字层，Wells Fargo 对公
    支票账户，实际是 1-4 月共 4 份月度对账单拼在一起的 32 页 PDF）。
    两个版本现在都会自动用 OCR 兜底解析：银行名称/账号/币种/整份文件
    期初期末余额（$44,940.37 → $36,534.93）都能可靠识别；能提取出
    约 525 条交易记录，但因为原始扫描件本身有明显倾斜和水印干扰，逐条
    交易的金额/日期识别错误率较高，加总金额与对账单应有净变动对不上，
    解析结果会明确弹出警告要求人工逐条核对（不能直接信任 OCR 金额）。
  如果之后遇到其它银行的真实对账单解析不准，同样可以把 PDF 发给我，我会
  按同样的方式（先看清 PDF 的实际文本结构，再补充针对性规则，最后用对账
  单自身的合计数字核对）继续扩展。
